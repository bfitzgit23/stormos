# The scratchpkg variant of the BFSOS ports tree

This document describes the copy of the BFSOS ports tree that is packaged for
**scratchpkg**, the package manager used by Venom Linux (`scratch`, `pkgbuild`,
`pkgadd`, `pkgdel`, `portsync`). The copy lives on the `scratchpkg` branch of
this repository; the main line keeps CRUX `pkgutils` (`Pkgfile`, `pkgmk`,
`prt-get`, and the `bfsos` pacman pipeline).

If you are looking for the normal BFSOS build, read the main branch instead.
Everything here applies to the `scratchpkg` branch.

## Why a separate copy

The two packaging systems disagree on four things that can only be settled one
way per tree:

| | CRUX `pkgmk` + BFSOS extension | scratchpkg |
|---|---|---|
| recipe file | `Pkgfile` | `spkgbuild` (this tree: `.spkgbuild`) |
| recipe variables | CRUX arrays (`source=(a b)`) | scalar shell (`source="a b"`) |
| where `build()` runs | inside the extracted source directory | from `$SRC`, the extraction root |
| patches / default build | applied and dispatched automatically | the recipe must ask for them |
| port names | any spelling (`libX11`) | lowercase, and the directory name must match |

Rather than teach one tree to be both, the `scratchpkg` branch is the same tree
re-expressed for scratchpkg: every port is a `.spkgbuild`, and the behaviour the
CRUX extension provided is supplied by a shared shell library the recipes source.

## Quick start

```sh
# install the packaging tools (once)
cd /usr/ports/core/scratchpkg && pkgbuild -i

# build and install a port plus its dependencies
scratch install bzip2

# search, inspect, sync
scratch search compress
scratch depends bzip2
scratch path bzip2
portsync

# upgrade everything
scratch sysup
```

`scratch` reads `/etc/scratchpkg.repo` for its repositories (one line per
collection) and `/etc/scratchpkg.conf` for build policy. Both are installed by
the `scratchpkg` port with BFSOS values.

## Recipe format

A port is a directory whose name matches the recipe's `name`:

```
ports/core/bzip2/
  .spkgbuild                     recipe
  bzip2-1.0.8-install_docs-1.patch   patch source, applied automatically
  install                        pre/post install / upgrade / remove hook
  .checksums                     md5sums (generated by pkgbuild on first build)
```

```sh
# description : Programs for compressing and decompressing files
# homepage    : https://sourceware.org/bzip2/
# maintainer  : BFSOS maintainers
# depends     : glibc

. /usr/libexec/bfs/spkgbuild-lib.sh

name=bzip2
version=1.0.8
release=1
source="https://www.sourceware.org/pub/bzip2/$name-$version.tar.gz bzip2-1.0.8-install_docs-1.patch"

build() {
	bfs_enter_srcdir || return 1
	bfs_apply_patches || return 1
	...build steps, staging into $PKG...
}
```

Notes on the pieces:

- **The file is named `.spkgbuild`, not `spkgbuild`.** `pkgbuild` takes the
  recipe name from the `PKGBUILD_BSCRIPT` variable in `/etc/scratchpkg.conf`,
  and it sources that config file *after* its own defaults, so the name is
  configurable. The `scratchpkg` port sets it to `.spkgbuild`. Set it back to
  `spkgbuild` if you prefer upstream names.
- **Header comments carry the metadata.** `pkgbuild` refuses a recipe with no
  description, and `scratch` resolves `# depends` entries by port name.
- **`name` must equal the directory**, and may not contain capital letters.
  That is why upstream spellings such as `libX11` and `SpiderMonkey` are
  `libx11` and `spidermonkey` here; the recipes note the original spelling.
- **`$PKG` is the staging root**, exactly as in CRUX, so the existing build
  steps work unchanged. `$SRC` is the extraction root, as in the CRUX extension.
- **`install`** scripts receive `$1` = `pre-install`, `post-install`,
  `pre-upgrade`, `post-upgrade`, `pre-remove`, `post-remove`, with `$2` = new
  version and `$3` = old version. The CRUX `post-install`/`pre-install` files of
  109 ports were wrapped into such scripts; the originals are kept next to them.
- **`renames=(...)`** from the CRUX recipes is a parallel array of local file
  names (SKIP keeps the URL basename) and is translated to scratchpkg's
  `<local-name>::<url>` source form. Names such as `.zipx`, `.xzblob` and
  `.noextract` stay useful: `pkgbuild` decides whether to unpack by the local
  extension, so those archives stay opaque until the recipe unpacks them.
- **Checksums** are a `.checksums` file next to the recipe. Most ports do not
  carry one; `pkgbuild` generates it on the first build, and `-m` skips checking.

### The build-conventions library

`/usr/libexec/bfs/spkgbuild-lib.sh` (shipped by the `scratchpkg` port, source:
`ports/core/scratchpkg/files/spkgbuild-lib.sh`) restores what the CRUX `pkgmk`
extension used to do around every recipe:

| helper | what it reproduces |
|---|---|
| `bfs_enter_srcdir` | cd into `$SRC/$name-$version`, else the single source directory |
| `bfs_apply_patches` | apply `*.patch`/`*.diff` sources, `-p1` then `-p0`, skip if already applied |
| `bfs_standard_build` | detect meson/configure/cmake/setup.py/Makefile.PL/Makefile and build it with BFSOS layout defaults (`--prefix=/usr`, `--sysconfdir=/etc`, `libdir=$BFS_PKG_LIBDIR`, `DESTDIR=$PKG`, tests off unless `run_tests=yes`) |
| `bfs_build_opts` / `bfs_build_opt_has` | the scalar-or-array `build_opt` handling of the extension |
| `_bfs_require_compat32_extension` | a no-op: under scratchpkg the 32-bit contract comes from the compat-32 preamble below |
| Qt6/KF6 prefix setup | `/opt/qt6` and `/opt/kf6` added to `CMAKE_PREFIX_PATH`, `PKG_CONFIG_PATH`, `CPLUS_INCLUDE_PATH`, `LIBRARY_PATH` |

Recipes that define their own `pkg_build()`/`build()` keep their steps verbatim;
the generated `build()` only adds the source-directory entry, the patch loop,
and the `pre_build`/`post_build` hook calls in the same order the extension used.

### compat-32

32-bit ports (marked by the CRUX `.32bit` marker) get a preamble that exports
`BFS_PKG_LIBDIR=/usr/lib32`, `-m32` compiler flags, `-L/usr/lib32` and a 32-bit
`pkg-config` search path; the library then adds `--host=i686-pc-linux-gnu` for
autotools and a cross file for Meson. No per-port cross files are needed.

## Building the whole tree

```sh
# every collection listed in /etc/scratchpkg.repo
sudo scripts/bfs-spkgbuild-all.sh

# one collection, four at a time, rebuilding what is already there
sudo scripts/bfs-spkgbuild-all.sh -c core -j4 --force

# build and install (resolves # depends first)
sudo scripts/bfs-spkgbuild-all.sh --install -c core

# inspect the work list first
scripts/bfs-spkgbuild-all.sh --dry-run
```

Packages land in `/var/cache/scratchpkg/packages` (`PACKAGE_DIR`). Because
scratchpkg has no repository index — the *ports tree* is the repository —
"publishing" a collection means keeping its `.spkgbuild` files in sync with
`portsync` and its built packages in the cache.

## Building a stage3 root filesystem from the tree

A stage3 is the packed contents of a built root filesystem. Build it by
installing into a target root with scratchpkg, then packing it with the tree's
stage3 builder:

```sh
# 1. install a base into a target root (chroot or a mounted partition).
#    scratch passes unknown options through to pkgbuild, which hands
#    --root=<path> to pkgadd, so dependencies land in the same root.
sudo mkdir -p /mnt/stormfs
sudo scratch install --root=/mnt/stormfs bzip2 zlib glibc ...
#    ...which is the same as, per port:
#    cd /usr/ports/core/bzip2 && sudo pkgbuild -i --root=/mnt/stormfs

# 2. pack it, zstd-compressed, excluding pseudo-filesystems and caches
sudo scripts/bfs-mkstage3.sh -r /mnt/stormfs -o bfs-stage3-$(date +%Y%m%d).tar.zst

# 3. restore anywhere
sudo tar --numeric-owner -xpf bfs-stage3-$(date +%Y%m%d).tar.zst -C /mnt/target
```

See the "Stage3 rootfs archive" section of the top-level README for the
packer's options (`-C xz`, `-x` extra excludes, `--dry-run`, verification).

## Producing and validating this copy

The conversion is scripted, not hand-edited:

```sh
# from a CRUX tree, produce the scratchpkg copy
python3 scripts/bfs-ports-to-spkgbuild.py --write             # Pkgfile -> .spkgbuild
python3 scripts/bfs-ports-to-spkgbuild.py --lowercase-names --write
python3 scripts/bfs-ports-to-spkgbuild.py --fix-deps --write  # '# depends' resolves

# validate it
python3 scripts/bfs-ports-to-spkgbuild.py --check             # structure + pkgbuild rules
find ports -name '.spkgbuild' -print0 | xargs -0 -n1 sh -n    # shell syntax
```

`--check` enforces the rules `pkgbuild` itself enforces (directory equals
`name`, lowercase `name`, numeric `release` between 1 and 99, a `version`
without `-`, a non-empty description, a `build()` function) plus the tree's own
conventions (the library is sourced when helpers are used, CRUX
pre/post-install scripts have an `install` counterpart).

## What this branch does not convert

- `bootstrap.sh`, the installer (`scripts/install-bfs-menu-current.sh`), the ISO
  builder and the `pkgutils`/`bfsos` pipeline still speak CRUX/pacman. On this
  branch they are kept for reference; the base system bootstrap remains a
  `pkgutils` build, and scratchpkg is used for the ports tree on top of it.
  Teaching the bootstrap to install the base with `scratch` is future work.
- The `bfsos`/`pacman` port does not apply here: use `scratch`, not `bfsos`,
  for installs on this variant.
- `.footprint` files (CRUX installed-file lists) are kept for reference;
  scratchpkg tracks files in `/var/lib/scratchpkg/db` and uses `.pkgfiles`.
- `profiles/init/overlays/{openrc,sysvinit}/**` still hold 118 generated CRUX
  `Pkgfile` variants (plus 16 `Pkgfile.before-*` backups inside the tree). They
  belong to the bootstrap's init-profile flow, which this branch leaves on
  pkgutils: they are overlay recipes applied *over* the ports tree by
  `bootstrap.sh`, and scratchpkg has no equivalent step, so converting them to
  `.spkgbuild` would produce recipes nothing consumes. The ports tree itself
  contains no `Pkgfile` at all.

### Known gaps

- Five `# depends` entries name things that are not ports in this tree:
  `filesystem` (from `sysvinit`; the port is `aaa_filesystem`), and `kpmcore`,
  `python3-pyqt6`, `qt6-tools`, `yaml-cpp` (from `calamares`). `scratch install`
  of those ports will report the missing dependency.
- A handful of CRUX recipes define `post_install()` shell functions instead of a
  `post-install` file; those are carried into the `.spkgbuild` unchanged, where
  scratchpkg does not call them. Convert them to an `install` script if you need
  their behaviour.
- 32-bit ports still rely on the `pkgutils`-era multilib layout (`/usr/lib32`).
  A `scratch`-native multilib (`lib32-*` ports building for a 32-bit target
  root) is future work.

## Verification status

The copy on the `scratchpkg` branch was verified as follows:

- 1380 ports converted; `--check` reports no problems for any of them;
- `sh -n` passes for all 1380 recipes and all 109 generated `install` scripts;
- every `# depends` entry resolves to a port in the tree except the five names
  listed under *Known gaps*;
- the conversion tool itself is checked by running it against the CRUX tree
  (`--write` then `--check`), and the library and generated scripts are shell
  syntax checked.

Not verified here: an actual `pkgbuild` run (the development host has no
scratchpkg, no compiler and no Linux userland), so the first real build on a
BFSOS machine should start with `-c core` and a small package such as
`ports/core/bzip2`.
